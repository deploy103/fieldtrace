Offline evidence playbook

정답이 안 보여도
근거는 남아 있다.

FieldTrace가 답을 바로 표시하지 못했을 때 사용하는 현장용 문제풀이 가이드입니다. 결과 0건, 후보 폭증, 부분 분석, 인코딩, 조각난 값, Blind SQL처럼 “값이 원문에 그대로 없는” 상황을 증거 위치에서 다시 시작해 해결합니다.

지금 분석 시작 설치·명령 전체 보기 1페이지 현장 가이드
01원본은 읽기 전용
02후보와 정답을 구분
03위치로 재현해 검증
!

“검색 결과 없음”은 “정답 없음”이 아닙니다. 정답이 인코딩됐거나 여러 레코드에 나뉘었거나, 참/거짓·응답 크기·시각 차이 같은 행동으로만 기록될 수 있습니다. 먼저 분석 범위를 확인하고 그다음 표현 방식을 바꾸세요.

Decision loop

정답까지 가는 6단계

각 단계의 질문에 답하지 못하면 다음 단계로 넘어가지 말고 진단·원문부터 확인합니다.

  1. 입력 확인파일·magic·압축·해시
  2. 범위 확인complete / partial / skip
  3. 신호 축소시각·source·행위별 묶기
  4. 표현 변환decode·조각·비교 결과
  5. 근거 역추적line·frame·record
  6. 정답 판정형식·길이·반증 확인

First response

증상별 대책

지금 보이는 증상을 검색하세요. 카드에는 바로 확인할 항목과 다음 행동이 들어 있습니다.

9개 표시
ZERO RESULT

검색 결과가 0건이다

대소문자보다 먼저 “정답이 원문에 연속 문자열로 존재하는가”를 확인합니다.

대응 순서
  1. run의 coverage와 진단을 확인합니다.
  2. 알고 있는 접두사, 핵심 도메인, 계정처럼 짧은 단서로 검색합니다.
  3. URL/Base64/Hex 변환 결과와 조각난 문자열을 확인합니다.
  4. 비교식·응답 크기·시간차로만 값이 드러나는지 봅니다.
TOO MANY

후보가 너무 많다

후보 개수를 정답 가능성으로 착각하지 말고 반복 캠페인을 하나의 행위로 묶습니다.

대응 순서
  • IP, User-Agent, endpoint, 시간 구간으로 그룹화합니다.
  • 완전히 같은 요청이 아니라 “추출 대상 식”과 “문자 위치”를 기준으로 묶습니다.
  • 최초 탐색, 본 추출, 종료 확인 구간만 남깁니다.
  • 대표 근거와 전체 건수를 함께 기록합니다.
PARTIAL

부분 분석으로 끝났다

일부 결과가 있다는 뜻이지 전체를 읽었다는 뜻은 아닙니다. 누락 이유를 먼저 분리합니다.

대응 순서
  • quick 예산이면 같은 입력을 full로 다시 분석합니다.
  • 손상·긴 줄·외부 도구 오류면 진단의 실패 단계와 위치를 확인합니다.
  • 미해석 레코드가 정답 구간인지 원문에서 별도로 확인합니다.
  • 완료 결과와 부분 결과를 섞어 “전체 확인”이라고 쓰지 않습니다.
INPUT

파일이 안 보이거나 형식이 이상하다

확장자를 바꾸기 전에 magic, 압축 내부 목록과 실제 파일 크기를 확인합니다.

대응 순서
  • 메뉴에서 다른 폴더 또는 경로 붙여넣기를 사용합니다.
  • ZIP은 목록·무결성·경로 탈출 여부를 검토한 뒤 임시 폴더에 풉니다.
  • 내용과 확장자가 다르면 수동 형식을 지정합니다.
  • 텍스트라면 UTF-8/UTF-16 BOM, CP949/EUC-KR 순으로 검토합니다.
TOOL MISSING

PCAP 또는 EVTX만 분석되지 않는다

해당 기능의 엔진이 빠졌을 가능성이 큽니다. 다른 형식의 성공과 혼동하지 않습니다.

대응 순서
  • ./run.sh doctor로 TShark와 python-evtx를 확인합니다.
  • TShark가 없으면 패킷 분석 완료를 주장하지 않습니다.
  • 대회 중 설치하지 말고 준비된 동일 OS용 패키지를 사용합니다.
  • 도구 버전과 사용 가능 field를 분석 기록에 남깁니다.
DERIVED VALUE

정답 문자열이 원문에 없다

문자열이 아니라 값을 설명하는 관측을 찾습니다. Blind SQL이 대표적인 경우입니다.

대응 순서
  • 같은 SELECT 대상과 행을 찾습니다.
  • 문자 위치별 비교 임계값과 최종 확인을 순서대로 정렬합니다.
  • ASCII/Unicode 값을 문자로 바꾸고 종료 위치를 확인합니다.
  • 복원값, 변환 규칙, 사용한 모든 근거 위치를 함께 보존합니다.
TIME

이벤트 순서가 이상하다

시간대 없는 자료를 UTC로 단정하면 공격 순서와 응답 지연을 잘못 해석할 수 있습니다.

대응 순서
  • timestamp_raw와 timezone_status를 확인합니다.
  • 근거가 있을 때만 default_timezone/default_year를 지정합니다.
  • 시간 미상 자료는 파일·레코드 순서를 보조 근거로 사용합니다.
  • 초 단위 로그에서 1초 지연 하나만으로 참/거짓을 확정하지 않습니다.
CORRELATE

한 파일만 보면 맥락이 끊긴다

여러 자료가 주어졌다면 동일 IP·도메인·계정·파일명을 출발점으로 관측을 묶습니다.

대응 순서
  • 모든 입력을 같은 case에 분석합니다.
  • correlate로 둘 이상의 source에 나온 값을 찾습니다.
  • timeline에서 앞뒤 사건을 확인합니다.
  • 동일 문자열만으로 동일 공격자나 인과관계를 확정하지 않습니다.
RECOVERY

중단·잠금·저장 오류가 났다

새 분석으로 덮기 전에 저장된 부분 결과와 원본 무결성을 확인합니다.

대응 순서
  • 다른 FieldTrace/SQLite writer를 닫습니다.
  • 디스크 여유와 사례 폴더 쓰기 권한을 확인합니다.
  • 다음 실행의 interrupted run 복구 진단을 확인합니다.
  • 원본 hash_status가 complete인지, 분석 중 size/mtime이 바뀌지 않았는지 봅니다.

Repeatable workflow

단계별 문제풀이 절차

정답을 빨리 찾는 것보다 같은 결론을 다시 만들 수 있도록 분석 경로를 남기는 절차입니다.

  1. 원본 고정과 입력 목록 작성

    원본을 수정하지 말고 파일명, 크기, SHA-256, magic을 기록합니다. 압축은 내부 목록과 무결성을 먼저 확인합니다.

    sha256sum ./input/evidence.* file ./input/evidence.* zipinfo -l ./input/evidence.zip unzip -t ./input/evidence.zip

  2. 분석 환경 진단

    필수 패키지, TShark, 사례 DB 쓰기와 디스크를 확인합니다. 선택 기능 누락을 전체 성공으로 해석하지 않습니다.

    ./run.sh doctor

  3. quick으로 지형 파악

    형식, 입력 수, 대표 후보와 오류를 먼저 봅니다. 이 단계의 목적은 정답 확정이 아니라 다음 질문을 정하는 것입니다.

    ./run.sh analyze ./input \ --profile quick \ --case ./cases/problem

  4. coverage와 실패 구간 확인

    complete인지, quick 예산이나 손상 때문에 partial인지 확인합니다. 정답이 누락 구간에 있을 가능성을 닫지 않습니다.

    • 처리 레코드 수와 실제 줄/패킷/record 수 비교
    • diagnostics의 stage, 이유, 다음 행동 확인
    • hash_status와 원본 변경 여부 확인

  5. full 또는 목적별 custom 실행

    무작정 모든 변환을 반복하지 말고 형식에 맞는 분석 항목을 선택합니다.

    ./run.sh analyze ./input/evidence.log \ --profile full \ --case ./cases/problem ./run.sh analyze ./input/capture.pcapng \ --type pcap \ --profile custom \ --tasks tcp_streams,object_extraction \ --case ./cases/problem

  6. 넓게 검색하고 좁게 검증

    정답 전체보다 접두사, 테이블명, endpoint, 계정처럼 짧고 설명 가능한 단서를 먼저 찾습니다.

    ./run.sh search --case ./cases/problem --text 'FLAG{' ./run.sh search --case ./cases/problem --text 'information_schema' ./run.sh search --case ./cases/problem --text 'SLEEP('

  7. 행위 단위로 재구성

    검색 결과에 값이 없으면 요청 순서, 응답 크기, 지연, 문자 위치, stream 같은 구조를 기준으로 조각을 다시 묶습니다.

    • 같은 source와 시간 구간인가?
    • 같은 추출 대상·행·문자 위치인가?
    • 재시도와 calibration probe를 제거했는가?
    • 값 종료 또는 다음 단계 전환을 확인했는가?

  8. 원본 위치로 반증

    후보를 만든 규칙이 아니라 실제 line, frame, EVTX record를 확인합니다. 다른 해석이 가능한지 함께 기록합니다.

    ./run.sh timeline --case ./cases/problem --limit 1000 ./run.sh correlate --case ./cases/problem --min-sources 2 ./run.sh report --case ./cases/problem --format html

  9. 정답 후보와 한계를 분리해 보고

    복원 문자열만 쓰지 말고 입력 hash, 변환 과정, 증거 위치, coverage, 신뢰도와 남은 반례를 함께 제출합니다.

Derived evidence

원문에 없는 값 찾기

정답은 파일 안의 연속 문자열일 수도 있지만, 여러 관측을 조합해야만 나타나는 파생값일 수도 있습니다.

표현 방식 관측 신호 재구성 방법 필수 검증
URL/Base64/Hex %7B, 긴 인코딩 토큰, 16진 바이트 깊이와 출력 크기를 제한해 단계별 변환 원문→변환 종류→결과 chain 보존
여러 레코드로 조각남 같은 세션·키·순번에 작은 문자열 반복 source, 시각, stream, sequence 기준 정렬 누락·중복·재전송 표시
Blind SQL 비교 ORD(MID(...)) > N, != N 대상·행·문자 위치별 비교 경로 복원 최종 확인과 다음 위치 전환, 종료 probe
응답 크기 기반 Boolean 같은 요청군에서 특정 status/bytes 두 집단 알려진 참/거짓 probe로 집단 의미 결정 캐시·오류 페이지·동적 길이 반례
시간 기반 Boolean SLEEP(n) 조건과 요청 간 지연 조건, 지연, 다음 요청 시작을 함께 비교 초 단위 정밀도·병렬 요청·네트워크 지연 반례
TCP/HTTP 조각 여러 frame의 같은 stream, 분할 body TShark 재조립 결과와 frame을 함께 확인 재전송·누락·불완전 복원 표시
EVTX 연쇄 프로세스 생성→네트워크→PowerShell 이벤트 ProcessGuid 우선, PID는 시간 범위 내 보조 provider/channel, PID 재사용·시각 불확실성

Case pattern

Blind SQL 로그 재구성

이번 유형처럼 플래그가 한 번도 평문으로 기록되지 않은 경우를 일반화한 절차입니다.

현재는 수동 후속 분석 필요

비교식 자체가 문자를 설명한다

SQLMap 계열 로그에는 추출 대상, 행, 문자 위치, 비교값이 요청 URI에 남을 수 있습니다. 아래와 같은 최종 검증 뒤 곧바로 다음 문자 위치로 이동했다면 해당 실행이 ASCII 67을 후보로 받아들였다는 강한 근거입니다.

ORD(MID( (SELECT value FROM challenge.flags LIMIT 0,1), 1, 1 )) != 67

67을 문자로 바꾸면 C입니다. 같은 방식으로 위치 2, 3…을 복원하고, 다음 위치에서 > 1도 거짓으로 끝나는 구간을 문자열 종료 후보로 봅니다. 예시는 설명용이며 실제 문제 답을 문서에 포함하지 않습니다.

Target SELECT value FROM challenge.flags
Row LIMIT 0,1
Position MID(..., 1, 1)
Candidate != 67 → ASCII "C"
1 / GROUP같은 SELECT·row·position을 묶기
2 / ORDER원본 line과 timestamp 순으로 정렬
3 / ACCEPT최종 비교 뒤 다음 위치 전환 확인
4 / STOP빈 다음 문자와 추출 종료 확인
비교 숫자만 모아서 바로 문자로 바꾸면 안 됩니다.

SQLMap은 calibration, 임의 큰 임계값, 재시도, 이진 탐색을 섞을 수 있습니다. 특히 병렬 요청이나 초 단위 timestamp만 있는 로그에서는 지연 하나만으로 참/거짓을 정하지 말고 “다음 임계값 선택”과 “다음 문자 이동”을 같이 확인하세요.

FieldTrace의 현재 경계

SQL 문법 형태 요청과 원본 line은 찾지만, Blind SQL의 문자별 결과를 자동으로 재조립하지는 않습니다. 따라서 후보가 수천 건이면 실패가 아니라 후속 재구성이 필요하다는 신호일 수 있습니다.

Format checklist

포맷별 마지막 확인

형식마다 놓치기 쉬운 근거와 수동 후속 분석의 출발점이 다릅니다.

웹 접근 로그

  • URI raw와 URL decode를 둘 다 확인
  • status와 bytes의 집단 차이 확인
  • User-Agent·endpoint·시간 구간 그룹화
  • SQLMap 문자 위치와 추출 대상 복원

일반 텍스트

  • 인코딩과 과도한 줄 길이 진단 확인
  • 접두사를 알고 있으면 TOML에 추가
  • Base64/Hex/URL chain 깊이 제한
  • line 번호와 원문 preview 대조

OpenSSH / sudo

  • 성공과 실패를 같은 계정·IP로 비교
  • 연도 없는 syslog 시각을 확정하지 않기
  • sudo COMMAND는 표시만 하고 실행 금지
  • 웹·PCAP의 IP와 교차 관측

PCAP / PCAPNG

  • doctor에서 실제 TShark 확인
  • DNS·HTTP·port를 frame으로 역추적
  • TCP stream 완전성은 unknown으로 유지
  • 추출물 hash와 원본 frame 확인

EVTX / Sysmon

  • event ID뿐 아니라 provider/channel 확인
  • ProcessGuid 연결을 PID보다 우선
  • record ID와 raw timestamp 보존
  • 손상 XML 뒤 레코드가 계속 처리됐는지 확인

ZIP / 묶음 파일

  • 자동 재귀 해제 대상이 아님
  • 항목명·압축률·무결성 먼저 검사
  • 절대경로, .., symlink 거부
  • 검토 후 별도 임시 폴더에만 해제

Evidence note

근거 기록 양식

분석 중 메모를 채우고 요약을 복사할 수 있습니다. 입력 내용은 전송하거나 저장하지 않습니다.

보안 메모: 이 페이지는 네트워크 요청을 만들지 않습니다. “요약 복사”를 누른 경우에만 운영체제 클립보드에 내용이 들어갑니다.

Answer gate

언제 정답이라고 말할까

도구의 finding은 출발점입니다. 제출 전 신뢰도와 반증 가능성을 분리합니다.

LOW

형태만 일치

접두사·정규식 또는 의심 규칙에만 일치. 문제 문맥·위치·변환 경로가 부족합니다.

MEDIUM

관측과 맥락 일치

원본 위치와 공격/추출 흐름이 맞지만 일부 문자, 순서 또는 종료 근거가 불완전합니다.

HIGH

재현과 종료 확인

독립적으로 같은 값을 복원하고 모든 문자·종료·입력 hash와 반례를 확인했습니다.

0 / 8

Stop conditions

파일만으로 풀 수 없는 경우

추측으로 빈칸을 채우지 말고 필요한 추가 입력을 구체적으로 식별하는 것도 올바른 결론입니다.

MISSING CONTEXT

문제 지문·정답 형식이 없다

무엇을 답해야 하는지 특정할 수 없습니다. 파일에서 관측 가능한 사실과 추정 가능한 후보까지만 보고합니다.

NOT RECORDED

필요한 값이 애초에 기록되지 않았다

응답 본문, 패킷 payload, EVTX 채널 등이 수집되지 않았다면 남은 로그만으로 복원할 수 없음을 명시합니다.

TRUNCATED

로그가 중간에서 끝났다

문자 일부까지만 추출됐거나 종료 probe가 없으면 부분 문자열과 마지막 확정 위치까지만 보고합니다.

ENCRYPTED

암호·키가 제공되지 않았다

암호 우회나 무차별 대입을 자동 수행하지 않습니다. 제공된 키·힌트·허용 범위를 요청합니다.

AMBIGUOUS

둘 이상의 값이 같은 근거를 만족한다

한 값을 정답으로 단정하지 말고 후보별 근거와 추가로 필요한 판별 자료를 나눠 기록합니다.

OUT OF SCOPE

지원하지 않는 포맷이다

형식을 억지로 텍스트로 읽지 않습니다. 안전한 오프라인 parser와 검증 fixture가 필요한 후속 작업으로 넘깁니다.

요청해야 할 추가 자료를 정확히 쓰세요.

“자료가 부족함” 대신 “17:52 이후 access.log”, “해당 tcp.stream의 양방향 packet”, “Security 채널 EVTX record 17846 이후”, “문제의 flag prefix와 시간대”처럼 다음 분석을 가능하게 하는 입력을 지정합니다.
